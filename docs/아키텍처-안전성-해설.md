# 안전성 해설 — 데이터 무결성과 비즈니스 규칙

> 결제와 수강권을 다루는 이 시스템이 장부가 틀어지지 않도록 어떤 장치를 두었는지 설명합니다. 각 장치는 코드나 테스트로 확인할 수 있는 것만 적었습니다.

## 1. 3중 방어

| 계층 | 장치 | 확인할 곳 |
|---|---|---|
| 진입·명령 | `proxy.ts`가 미인증·탈퇴·약관 미동의 요청을 걸러낸다. 쓰기는 명령 레일(`runCommand`)을 지나며 권한·통제 스위치를 확인하고 감사 기록을 남긴다. | `proxy.ts`, `lib/commands/`, `lib/commands/rail.guard.test.ts` |
| 도메인 격리 | 5개 모듈이 테이블을 나눠 소유하고, 모듈 간 통신은 아웃박스의 과거형 사실로만 한다. | `lib/architecture/module-map.ts`, `lib/architecture/boundaries.guard.test.ts`, `lib/wiring/outbox.ts` |
| DB | 중요한 쓰기는 `SECURITY DEFINER` 함수로만 하고, CHECK·UNIQUE·트리거로 상태와 금액 규칙을 강제하며, RLS로 타인의 행을 읽지 못하게 한다. | `supabase/migrations/`, `supabase/tests/` |

한 계층이 뚫려도 다음 계층이 막도록 같은 규칙을 앱과 DB에 겹쳐 두었습니다.

## 2. 테이블 소유권(R1)이 주는 안전성

- 문제: 모듈이 서로의 테이블을 직접 조회·수정하면, 한 곳의 변경(예: 결제 정책)이 다른 모듈의 데이터에 의도치 않은 영향을 줍니다.
- 방식: `orders`는 주문 모듈이, `payment_events`·`payment_attempts`는 결제 모듈이, `entitlements`는 이용권 모듈이 씁니다. 다른 모듈의 상태가 필요하면 직접 읽지 않고 아웃박스로 온 사실에 반응합니다. 새 테이블이나 DB 함수는 소속을 적지 않으면 경계 가드 테스트가 실패합니다.

## 3. 결제와 수강권 부여

- **재검증**: 결제창을 열기 전과, 결제하기를 누른 시점, 승인 결과가 돌아온 시점에 같은 규칙(체크아웃 가드)을 서버에서 다시 통과시킵니다(`lib/guards/checkout/`).
- **중복 반영 방지**: 웹훅과 승인 복귀가 겹쳐도 같은 결제가 한 번만 반영되도록 결제 시도 식별자와 원장 규칙을 두었고, 통합 테스트로 확인합니다(`lib/payment/payment-chain.integration.test.ts`).
- **원자성**: 결제 사실을 원장에 기록하는 것과 아웃박스 적재는 같은 트랜잭션에서 합니다. 이후 주문 반영과 이용권 부여는 아웃박스 배달로 이어지며, 실패한 메시지는 재시도하고 한도를 넘으면 DLQ에 남겨 관리자가 처리합니다.

## 4. 상태 전이

- 주문은 `orders.status`(`PENDING`, `APPROVED`, `REJECTED`, `CANCELLED`)와 `orders.payment_status`(`UNPAID`, `PAID`, `PARTIALLY_REFUNDED`, `REFUNDED`, `WAIVED`)로 승인 상태와 결제 상태를 나눠 관리합니다.
- 개설강의는 `OPEN`, `CLOSED`, `CANCELLING`, `CANCELLED`이고, 종료는 `ended_at` 기록으로 남깁니다.
- 상태 변경은 DB 함수와 트리거가 허용한 전이만 통과시키고, 전이마다 사유와 행위자를 기록합니다. 환불·종료·폐강처럼 되돌리기 어려운 경로는 기록이 원장에 남도록 했습니다.
- 앱의 삭제 대신 소프트 삭제·비활성화를 쓰고, 원장성 테이블은 수정·삭제를 트리거로 막았습니다.
