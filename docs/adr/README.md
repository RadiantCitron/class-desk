# class-desk 아키텍처 결정 기록 (ADR Registry)

> **문서 목적**: `class-desk`의 핵심 아키텍처 의사결정(Architecture Decision Records)을 투명하게 보존하고, 시스템의 주요 트레이드오프와 설계 원칙을 설명하는 기술 레지스트리입니다.

---

## 핵심 아키텍처 결정 일람 (Architecture Decisions)

주요 결정을 이 문서 안에서 완결되게 읽을 수 있도록 표로 정리했습니다.

| 식별자 | 아키텍처 결정 명칭 | 직면한 문제 및 배경 | 채택한 결정 및 구현 방식 | 핵심 이유 및 트레이드오프 |
|---|---|---|---|---|
| **ADR-0004** | 부분 환불 시 수강 권한 즉시 회수 | 다회차 강의 중 일부 회차 경과 후 환불 시 수강 권한 유지 여부 불명확 | 학생 귀책에 의한 부분 환불 시 잔여 수강 권한(디스코드 역할 등)을 즉시 회수하고 수강 종료로 처리 | '일부 금액 환불 = 수강 포기'라는 명확한 계약 원칙을 확립하여 이중 수강 부정행위 방지 |
| **ADR-0006** | 개설강의 단일 쓰기 경로 강제 | 여러 화면과 API에서 개설강의 속성을 임의로 직접 UPDATE할 경우 무결성 훼손 | 모든 개설강의 변경은 파라미터가 엄격히 검증된 단일 DB RPC 함수(`update_course_offering`)로만 강제 | 쓰기 경로를 단일화하여 상태 전이 유효성 검증과 이벤트 발행을 원자적으로 보장 |
| **ADR-0012** | UI 계층과 백엔드 비즈니스 로직 완전 격리 | UI 컴포넌트 내에 Supabase 직접 쿼리나 도메인 가드가 침투하여 결합도 증가 | Tailwind v4 + shadcn 기반의 5계층 UI 구조(`ui/`)를 정립하고, 프론트엔드는 순수 View 모델만 다루도록 격리 | 향후 UI 프레임워크나 디자인 시스템을 전면 개편하더라도 백엔드 도메인 코드는 0 수정 보장 |
| **ADR-0015** | 통합 명령/조회 레일 (Command Rail) | 서버 액션별로 권한 체크, 감사 로깅, 통제 스위치 검사가 제각각 구현되는 문제 | 모든 쓰기(Command)와 조회(Query) 요청이 단일 감사 레일(`runCommand`, `runQuery`)을 통과하도록 강제 | 단일 진입로에서 전역 비상 차단 스위치, 액터 인가, 감사 로그(`audit_logs`)를 기계적으로 기록 |
| **ADR-0019** | 수강 권한 입구/출구 명시화 | 수강생에게 언제 권한이 주어지고 왜 회수되었는지 사후 추적이 어려운 문제 | 이용권 테이블에 부여 근거(`grant_cause`)와 회수 사유(`revoke_reason`)를 ENUM 데이터로 반드시 기록 | 수강생 CS 문의 발생 시 이용권 발급/회수 이력을 원장에서 근거와 함께 소명 가능 |
| **ADR-0020** | 직권 수강 부여 시 결제 면제 사실 기록 | 관리자가 지인이나 이벤트로 무료 수강을 부여할 때 장부와 주문이 누락되는 문제 | 직권 부여 시에도 일반 수강과 동일한 정식 주문을 생성하되 결제 상태를 `WAIVED`(면제)로 기록 | "모든 수강은 주문에서 출발한다"는 R1 단일 원장 불변조건을 지키면서 예외 수강을 투명하게 관리 |
| **ADR-0021** | 폐강 집행의 명시적 분리 | 폐강 시 시스템이 무차별적으로 전액 자동 환불을 돌리면 PG 한도 초과나 정산 오류 유발 | 폐강 상태(`CANCELLING`)로 전이 후, 관리자가 학생별 계좌/결제 상태를 확인하여 명시적으로 환불 처리한 뒤 완료 | 금융 거래의 사고 위험을 줄이고 예외 상황(이미 취소된 결제 등)에 안전하게 대응 |
| **ADR-0022** | 강의 종료 수명주기 및 권한 자동 회수 | 종강 후에도 수강생의 디스코드 역할이나 강의실 입장이 방치되는 문제 | 크론 잡(`cron/outbox`)을 통해 종강일 다음 날 이용권을 일괄 자동 회수하고 상태를 `ENDED`로 전이 | 1인 운영자의 수작업 부담을 제거하고 보안 권한의 만료를 시스템이 자동으로 집행 |
| **ADR-0023** | 회차 일정의 물리적 행(Row) 관리 | 강의 일정을 단일 텍스트나 JSON 배열로 다루면 특정 회차 휴강/일정 변경 시 추적 곤란 | 회차마다 독립된 물리적 행(`course_offering_sessions`)을 생성하고 개강/종료일은 행 집합에서 계산 | 특정 회차의 시각 변경, 보강, 취소를 개별 행 단위로 안전하게 다루고 무결성 보장 |
| **ADR-0025** | 버전화된 환불 정책 표 (Policy Versioning) | 법령이나 약관 개정 시 기존 결제자의 환불 계산식이 소급 적용되어 분쟁 발생 | 환불 정책을 버전 붙은 독립 레지스트리로 관리하고, 주문 생성 시점에 적용 정책 버전을 주문에 영구 고정 | 과거 결제자는 결제 당시 약관에 따라 환불받고, 신규 결제자는 새 약관을 적용받는 완벽한 계약 일관성 확보 |
| **ADR-0026** | 수강 포기 사실의 원장 이벤트 기록 | 수강 취소·환불 사유가 생길 때마다 주문 테이블에 임의의 컬럼이나 상태값을 추가하는 안티패턴 | 주문 상태는 표준 `CANCELLED`를 유지하고, 취소 사실(원인, 경과 회차, 위약금)은 `order_events` 원장에 기록 | 테이블 스키마의 오염 없이 다양한 비즈니스 취소 사유를 무한히 확장 가능하게 지원 |
| **ADR-0028** | 개설강의 변경 사실의 DB 원장 원자적 기록 | 관리자가 강의 시간이나 정원을 변경한 후 무엇을 바꿨는지 추적이 안 되는 문제 | 모든 개설강의 속성 변경 시 `course_offering_events`에 이전/이후 값(`before`, `after`)을 동일 트랜잭션으로 기록 | 관리자 임의 변경에 대한 완벽한 감사 추적성(Audit Trail)과 데이터 대사 기반 제공 |
| **ADR-0029** | 불변 법칙과 유연한 원칙의 분리 | 지나치게 엄격한 시스템 제약으로 인해 운영자가 현실의 돌발 상황에 대응하지 못하는 경직성 | 절대 어길 수 없는 물리 법칙(금액 불변 등)과 운영 원칙을 가르고, 원칙의 예외는 명시적 사유 기록 하에만 허용 | 시스템의 무결성을 깨뜨리지 않으면서도 1인 운영자의 현실적 예외 처리 유연성을 동시에 확보 |

---

## 💡 ADR 설계 및 운영 원칙

1. **단일 원장과 사건 기반 기록**: 상태를 덮어쓰지 않고 변경 사실을 이벤트 원장(`events`)에 함께 기록합니다.
2. **외주 의존성 격리**: 인증(Supabase Auth)이나 결제(Toss Payments)와 같은 외부 서비스는 철저히 파사드와 어댑터 뒤에 격리합니다.
3. **불변조건 우선**: 코드가 아닌 데이터베이스 레벨(CHECK, UNIQUE, RLS, SECURITY DEFINER)에서 비즈니스 불변조건을 강제합니다.
